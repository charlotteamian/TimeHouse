## 一、心率对不上

### 现象

手表侧（强度健身，11 分钟）：平均 78 / 最大 113。
App 侧（07-26 18:35 · 11:10）：平均 73 / 最高 88 / 最低 64。

### 根因（按影响排序）

**A. 同步时机太早 —— 主因。**
`finishSession()`（MainActivity.java:990）在用户点"结束"的那一瞬间就调用
`syncHeartRateForRecord(..., silent=true)`。此刻手表配套 App（小米运动健康 / 华为 / 佳明）
几乎不可能已经把这次运动的心率序列推进健康连接——它们按自己的节奏同步，往往是几分钟后
或下次打开时。所以读到的是**已经在健康连接里的被动后台心率**（每几分钟一次的抽样，静息值）。
73 / 88 / 64 正是被动抽样该有的样子，不是运动段该有的样子。

**B. 一旦写错就再也改不回来。**
记录卡的"同步手表心率"按钮只在 `record.hrAvg == 0` 时渲染（MainActivity.java:2388）。
第一次拿到脏数据后按钮消失，没有任何手动重试路径。A + B 一起，构成"永久性错误值"。

**C. 窗口两端各留了 2 分钟静息。**
`readHeartRate()`（:2077-2078）用 `[结束时间 − 时长 − 2min, 结束时间 + 2min]`。
这 4 分钟的静息心率会拉低平均、并且 `min` 基本上必然来自热身前/结束后，没有训练学意义。
更关键的是，真实开练时间其实已经存在——`sessionStartEpochMillis`（:169、:774）
被赋值后**从未被使用**，窗口却靠反解格式化字符串 `"11:10"` 重建。

**D. 不区分数据来源、不做时间加权。**
`applyHeartRate()`（:2115）把窗口内所有 `HeartRateRecord` 一视同仁，不看 dataOrigin，
也不读手表自己的 `ExerciseSessionRecord`；平均是"样本算术平均"，而手表给的是时间加权平均。
采样密度不均时两者必然有几个 bpm 的差。

### 设计

1. **异步重试代替瞬时同步。** 每条记录带 `hrSyncState`：`NONE / PARTIAL / OK`。
   结束时试一次（大概率 PARTIAL），随后在 App 回到前台、打开记录页时自动重试，
   24 小时内取到 OK 就停；按钮**永远可见**（"重新同步手表心率"）。

2. **加入数据质量门槛，不合格不写入为正式值。**
   合格判据：窗口覆盖率 ≥ 60%（有样本的分钟数 / 训练分钟数）**且** 采样密度 ≥ 2 点/分钟。
   不合格时标注"低采样 · 可能手表还没同步完"，并保留重试，不冒充准确值。
   —— 这一条单独就能挡掉现在这次错误。

3. **窗口用真实起止。** 落盘 `startEpochMillis` / `endEpochMillis`（复活那个死字段）。
   查询用 `[start − 90s, end + 90s]` 容忍时钟偏差，**统计只取 [start, end] 内的样本**，
   窗外样本只画进曲线不进指标。

4. **时间加权平均。** `avg = Σ(hr_i × Δt_i) / ΣΔt_i`，Δt 为到下一样本的间隔、上限 30s
   （防止一个长空档被当成一段恒定心率）。max/min 只在 session 窗口内取。

5. **优先对齐手表自己的运动记录。** 申请 `READ_EXERCISE`，读窗口内重叠的
   `ExerciseSessionRecord`；存在就用它的起止作为权威窗口，并显示
   "已对齐手表运动记录：强度健身 18:24–18:35"。这是唯一能让两边数字真正对上的做法。
   顺带可读 `READ_TOTAL_CALORIES_BURNED` 把手表的消耗一起归档。

6. **让偏差自解释。** 记录卡显示来源 App 名、采样点数、覆盖率：
   "来自 小米运动健康 · 42 点 · 覆盖 91%"。对不上时用户一眼能看出是谁的问题。

> 说明：手表的 session 窗口和 App 的计时窗口本来就可能差一两分钟（热身段），
> 目标是"一致到可解释"，不是逐位相同。

## 二、说好 40 分钟，实际 10 分钟

### 根因（三处叠加，全部可验证）

**A. "预计 40 分钟"是一个从未被验算的标签。**
`startProgramSession()`（:7207）写死 `minutes = 40`（初级）/ 55；
`RecommendationEngine.estimatedMinutesFor()`（:404）在 `requested != 0` 时
**直接把这个 40 原样回显**，从不核对实际处方。

**B. 时间预算只用来查表定"动作数"，且查完就被推翻。**
`targetExerciseCount()`（:382）把 40 分钟映射成 5 个动作，再被
`intensity.maxExercises()` 截断（LOW=4）→ 4 个动作。
**紧接着**（:7233）阶段处方整体覆盖每个动作的组数与休息：
适应期 = `Prescription(2, "10-12", "5-6", 90)`，初级 `adjustSets` 后仍是 2 组。
定动作数时假设的每组时长（`estimateFromExercises` 里写死 60s/组）与最终生效的
处方之间没有任何回算——闭环从来没有闭上。

**C. 算出来就是 11 分钟。**
4 动作 × [2 组 × ~30s + 1 × 90s 休息 + ~25s 切换] ≈ 11 分钟。实测 11:10，完全吻合。
所以**不是随机误差，是模型缺失**。

### 设计：把时长从"标签"变成"被求解的量"

给 `Prescription` 补结构化字段（现在 `reps` 是字符串 `"10-12"`，无法计算）：

| 字段 | 含义 |
|---|---|
| `repsLow / repsHigh` | 解析自 "10-12" |
| `kind` | `REPS` / `HOLD_SECONDS` / `TIME_DISTANCE` |
| `holdSeconds` | 计时类动作（平板、死虫、鸟狗、臀桥保持）的每组秒数 |
| `secondsPerRep` | 节奏，默认 3s（1s 向心 + 2s 离心），可按人校准 |
| `perSide` | 单侧动作，工作时间 ×2 |

新增领域类 `SessionTimeModel`：

```
每组工作秒 = kind==HOLD ? holdSeconds : 中位次数 × secondsPerRep × (perSide?2:1)
每动作秒   = 组数×工作秒 + (组数−1)×休息 + 切换 25s
课程分钟   = 热身 4 + Σ每动作 + 放松 3
```

**求解顺序（计划课）**：阶段处方是科学约束，不能为了凑时间改动；能动的是动作数量、
辅助内容、有氧。
1. 先按当日分化算**必需动作集**（见第三节，覆盖每个 movement pattern）；
2. 算真实时长 T；
3. `T < 可用时间`：按优先级补 —— ①把 `aerobicMinutesPerWeek` 真正排进课表
   （现在它只是一段文字，从没进过训练流程） ②加辅助动作 ③在阶段上限内加组；
   补不满就**如实显示"今天 12 分钟，适应期本来就轻"**并解释原因，而不是硬塞。
4. `T > 可用时间`：先砍辅助，再砍到最低有效剂量，仍超时就提示"今天只够做 A/B"。

**闭环校准**：每组的实际用时本来就在计时器里。训练后对比"预计 12 / 实际 11:10"，
滚动更新该用户的 `secondsPerRep` 与切换时间。跑几次之后估算不会再偏。

## 三、动作编排（比时长更严重的问题）

### 根因

**A. `ProgramFocus.patterns()` 从未参与生成。**
全项目对它的唯一引用是详情页展示 `focus.regions()`（:7148）。
分化模板里精心定义的 蹲/推/拉/髋铰链/抗旋转 完全是死数据。

**B. 计划课走的是"纯排序取前 N"，没有任何动作模式覆盖保证。**
`startProgramSession` 把 focus 拼成一句 `intentText`（"腿臀胸背核心"）丢给关键词解析器
→ `intent.targeted = true` → 走 `selectTargeted()`（:301），它只是按分数排序取前 N。
带 pattern 覆盖逻辑的 `selectFullBody()`（:315）**只在"不知道练什么"时才会被调用**。

后果就是截图里的全身 A：墙壁俯卧撑 / 臀桥 / 死虫 / 鸟狗 —— 没有蹲、没有拉，
两个近乎同质的抗伸展核心动作占掉一半名额。

**C. 评分与日期无关 → 全身 A / B / C 会取到几乎相同的动作。**
`score()`（:270）只看部位、模式、标心、证据、难度，没有任何"最近练过"的项。
A 和 B 的 goalRegions 只差一个"肩"，排序结果高度重合。分化的意义被抵消。

**D. 每次开练才现算 → 日历上没有内容可展示。**
这也是"给出健身日历、每日安排的动作"必须先解决的前提。

### 设计

1. **生成计划时一次性预生成全部 8 周 × N 天的课表并落盘**，而不是开练现算。
   只有这样才能同时保证：跨天不重复、每肌群每周 ≥2 次真的成立、日历可见、
   替换后能记住。
2. **按 focus.patterns() 做槽位填充**：每天的课表 = 一组"模式槽位"
   （如 LOWER 日 = 蹲 ×1 + 髋铰链 ×1 + 单腿 ×1 + 抗伸展 ×1），
   每槽在通过安全/器械过滤的候选里选分最高、且**近 N 天未使用**的。
3. **加入新鲜度项**：`score` 增加 `−(最近 14 天使用次数 × 权重)`，
   并在预生成时全局去重，保证 A/B/C 真的不同。
4. **替换动作**：锁定该槽位的 pattern，给几个候选让用户挑，选择持久化到那一天。

**实测效果**（模拟器，增肌 / 初级 / 每周 3 天）：
全身 A = 杯式深蹲(蹲) + 哑铃卧推(推) + 弹力带下拉(拉) + 死虫(抗伸展) + 臀桥 + 鸟狗；
全身 B = 罗马尼亚硬拉(髋铰链) + 上斜俯卧撑(推) + …… + 弹力带外旋(稳定) + 坐站 + 台阶上步。
两天零重复，分化声明的每个动作模式都被覆盖。

### AI 参与挑动作

**分工**：安全 / 器械 / 证据过滤永远在本机做；AI 只在过滤后的候选里给**排序偏好**，
组数、次数、休息由周期计划决定，AI 不碰。

**做法**（不逐天问——8 周 × N 天 × 4 槽位太贵也太散）：
按分化（FULL_A / UPPER / …）一次性问，每个分化的每个槽位要 3-4 个按推荐顺序排的动作 id。
`ProgramComposer.composeDay(..., slotPreferences)` 拿到偏好后，优先选偏好里靠前、
且最近没练过的；偏好里没有可用的就退回本地评分。跨天去重和安全过滤不会被 AI 绕过。

**隐私**：设置页原本就承诺"伤痛和心率等健康数据不会发送"。这里保持——
伤痛只用于本机过滤，发给 AI 的是过滤**之后**的动作清单，AI 不知道你哪里痛。

**降级**：AI 关闭 / 没填 Key / 网络失败 / 返回不可用 → 本地槽位编排，计划一定生成得出来。

## 四、训练日历

### 现状

`programDoneKeys` 是 `"周:日"`（:231），**完全没有日期概念**；
`nextProgramSession()`（:6903）永远返回"下一个未完成的格子"。漏练自动顺延，
8 周计划会无声地拉长成 12 周，而周期化的强度曲线是按周设计的——顺延等于把曲线拉平。

### 设计

- `TrainingProgram` 增加 `startDate` + 每周固定的星期几（如一/三/五）。
  生成时展开成 `ScheduledSession { date, week, dayIndex, focus, phase, items[], status }`，
  `status ∈ PLANNED / DONE / SKIPPED / MOVED`。
- 日历视图：月/周网格，每格标力量 / 有氧 / 休息 / ✓已完成 / 漏练。
  点开 → 当日课表（动作卡、组次、预计时长）→ 可替换动作、可整体挪到别的日期、可标跳过。
- 有氧任务也进日历（现在只是 `aerobicNote` 一段文字）。
- **漏练策略**（成熟 App 都有明确规则，这里必须定）：
  建议默认**保持周结构**——漏了就是漏了，本周剩余照常；
  周末结算，若本周完成率 < 60% 则自动把该周重复一次（而不是整体顺延）。
  连续两周 < 50% 则提示下调每周天数、重新生成。给用户一个"顺延/不顺延"开关。

## 五、引导式训练 + 语音

### 现状

训练页（`renderSession()`，:779）是"秒表 + 手动点完成本组"。
没有任何语音，只有休息结束的一声 `ToneGenerator` beep（:894）。
休息倒计时用 `CountDownTimer` 250ms tick（:826），做报数会漂。

### 设计

**先补数据：动作要区分计次 / 计时。** 数据集 `exercises_1324.json` 目前只有
instructions，没有这个字段。做法：按 category / pattern / 名称规则化推断
（plank、hold、dead bug、bird dog、bridge 类 → 计时），生成后人工校对进入推荐池的高频动作，
其余默认计次。单侧动作同时打 `perSide` 标记。

**已实现的判定**：`ExerciseTempo` 用动作名（平板/支撑/静蹲/侧桥…）+ 动作模式（单腿）
+ 动作自带处方里的 `/侧` 标记做确定性判断，不引入额外数据文件，可被领域测试覆盖。
死虫就是靠自带处方 `"8-10/侧"` 认出来的——阶段处方覆盖成 `"10-12"` 后这个信息不能丢。

**播报词表（16 条，已生成）：** 准备 / 开始 / 换边 / 完成 / 休息 / 下一个动作 + 一到十。
按用户决定，**先只做倒计时读秒 + 口令，不做逐个报数**。

**实现**（`scripts/generate_voice_cues.py` + `app/.../VoiceCues.java`）：
- 预生成音频：macOS `say -v Tingting -r 160` → ffmpeg 掐掉首尾静音 → **Ogg/Opus** →
  `res/raw/voice_*.ogg`，共 68KB。用 `SoundPool` 播放。
  用 Opus 不是 Vorbis：homebrew 的 ffmpeg 默认不带 libvorbis，libopus 有；
  Android 从 API 21 起原生支持 Ogg 里的 Opus，minSdk 28 够用。
- 不用系统 `TextToSpeech`：报数必须踩在秒上，TTS 的初始化和排队延迟会让"三"落到第四秒；
  国产 ROM 也不保证装了中文引擎。词表固定，预生成完全够。
- 计时器换成对齐 `SystemClock.elapsedRealtime()` 的 `Handler.postDelayed`（200ms 一跳），
  消除 `CountDownTimer` 的累加漂移。
- `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`：放着音乐也能听清口令，且不打断音乐。
- 设置页有开关 + 试听。校验：`generate_voice_cues.py --check`
  （检查 16 个文件都在、单条 ≤1.6 秒，太长就压不进一秒的节拍）。

**训练页已改成引导流**：`SessionPhase` 四态 —— PREPARE（看示范）→ COUNT_IN（三二一）
→ WORK（计时动作走倒计时并在最后 10 秒读秒、单侧动作中点报"换边"；计次动作走秒表）
→ REST（倒计时，可 +20 秒或跳过）→ 自动回到 COUNT_IN 进下一组 → 动作做完自动进下一个动作
（回到 PREPARE，秒表归零）。手动按钮全部保留。

## 六、两条线：计划训练 vs 临时加练

用户点出的核心。这两者**求解的东西根本不同**：

| | 计划训练 | 临时加练 |
|---|---|---|
| 输入 | 目标 + 水平 + 每周天数 + 起始日期（一次性） | 一句话意图 + 现在有多少时间 + 手边器械 + 今天状态 |
| 求解对象 | 8 周的**总量分配**：每肌群每周组数 → 分到每天 → 再选动作 | 单次课的即时组合 |
| 时长 | **结果**（由处方推出），可用时间只用来裁剪辅助内容 | **硬约束**（说 15 分钟就必须 15 分钟），组数/动作数是结果 |
| 约束 | 跨天不重复、频率 ≥2 次/周、周期化曲线、进阶规则 | 不能破坏计划：避开今天/明天要练的肌群 |
| 记账 | 计入计划进度 | 计入"额外量"，**回写周总量**（加练也是训练量，影响恢复） |
| 生成时机 | 一次性预生成落盘，日历可见 | 现场生成，不写进计划 |

### 临时加练线（`AdHocIntent` + `AdHocPlanner`）

1. **读恢复状态**（`RecoveryState`）：从训练记录聚合各部位上次练的时间。
   24 小时内练过的部位直接排除，48 小时内降权（ACSM：同一肌群两次刺激间约需 48 小时）。
2. **读计划冲突**：看日历上明天那节课要练的部位，避开它。
3. **升级意图解析**（`AdHocIntent`）：
   - 否定 —— "不要练肩"、"腿不练"（句尾否定），且"练腿不练背"里的否定正确归给背；
   - 时间 —— "15分钟"、"二十分钟"、"半小时"、"一刻钟"、"一小时"；
   - 目的 —— "出汗/心肺"→循环模式（休息 30 秒）；"很累/酸/僵"→恢复模式（只留低关节压力动作，≤2 组）。
4. **时长是硬约束**：先按预算定动作数，再**从大往小试组数**，找塞得下的最大组数；
   组数掉到 1 组还塞不下就减动作数再试——与其 5 个动作各 1 组，不如 3 个动作各 2-3 组。
5. **输出说明代价**："这次加练会占用本周容量：背 6 组、肩 3 组。"

**一条重要的边界**：用户点名了部位（"练背"），冲突只作为**提示**，不能把它挤出计划。
第一版把"明天要练背"的惩罚也加在点名的部位上，结果说"练背"却排出 6 组肩——
已修正为点名部位不扣分，且只在候选实在不足（<2 个）时才用别的部位补位。

### 把两条线连起来的机制：周容量台账

`WeeklyVolumeLedger`：每肌群本周已完成组数，计划课和加练记同一本账。
折算按 Schoenfeld 的直接组/间接组惯例：动作主要部位记 1 组，其余目标部位各记 0.5 组。
建议区间按训练水平取（初级 6-14、中级 10-20、进阶 12-24，见
`GuidelineRefs.VOLUME_DOSE_RESPONSE`）。超上限就在生成加练时警告；
没指定部位时优先补本周欠刺激的肌群。

台账要有结构化数据才算得出来，所以 `SessionRecord` 增加了
`itemStats`（`动作id|组数|是否完成`）。老记录没有这个字段，不计入台账。
